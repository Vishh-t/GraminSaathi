### How the analysis now chooses a scheme
Applicant = `FinancingSchemeService.resolveApplicant(...)`: a baseline (age 30 via `BASELINE_AGE`, rural, greenfield, state from the village, sector/sub_sector from the category) overlaid with the optional `applicant` on `AnalyzeRequest` (client facts win, except state/sector/sub_sector, which the village/category decide). Without `applicant`, schemes needing caste/gender/income/education/etc. are excluded, so the baseline result is only Mudra Kishor/Tarun (+ PMEGP for big loans), identical in every village — all central, since no state scheme's gating criteria are met without applicant details. Candidates must also: have interest_rate (own or estimated, section 2.11) + tenure >= 1 year (fractions like 2.5 are fine), be central or in the village's state, not be urban-only, list the sector in `target_sector`, have the loan amount inside `loan_amount_range` (`max: 0` = no limit), and pass their JsonLogic rules. Options with `repaymentMonths <= 0` (moratorium >= tenure) are dropped. Repayment maths: tenure in months (2.5y = 30), interest accrues through the moratorium and is capitalised, then EMI over the remaining months (on the full loan — a subsidy is never used to lower the EMI, only the ranking). Ranking: affordable first (section 2.10), then lowest net cost, then lowest EMI, then scheme_id. Primary = first. Comparison table = first 5, each row carrying `totalRepayment`/`estimatedSubsidy`/`netCost`/`rateEstimated`/`affordable`.

## 2. Data findings (differ from the handoff)
1. 230 records but only **201 unique scheme_ids** (51 central / 150 state): 28 exact duplicates + 1 near-duplicate (`state-cg-godhan-2020`, name differs). Deduped in the loader, file untouched.
2. Vocabulary is **46** variables (handoff says ~45). All used; none missing.
3. `interest_rate` in the dataset is **percent** (11 = 11%). `FinancialResult.interestRateAnnual` is a **fraction** (0.11). Convert at the boundary (done in `FinancialCalculatorService`).
4. `calculation_type` values actually present: pct_of_cost_capped 90, interest_rate_reduction 45, pct_of_loan_capped 37, per_unit_or_in_kind 11, composite 7, equity_or_uncapped 6, guarantee_cover_pct 5. **No** top-level `flat_grant_or_cap`, `pct_of_loan_uncapped`, `text_only_see_note` — but `pct_of_loan_uncapped` appears as a **composite component** (PM Vishwakarma), so the calculator must still support it.
5. 2 composites list only ONE component: `state-ap-ysr-cheyutha-2020`, `state-ml-prime-2020`.
6. **PMEGP data bug:** its special-category enhancement condition (tagged `high` confidence) is true for everyone (category list includes `general`, rural/urban covers both). A general urban applicant would get 35% instead of 15%. Single-tier enhancement can't express PMEGP's 2x2 matrix. Fix before demo. Other "high" conditions may have the same flaw; spot-check.
7. Rule operators used: `==, and, in, >=, <=, or, !` — all supported by json-logic-java.
8. Only 47 of 201 schemes are loan-type (interest_rate + tenure >= 1y); 151 have no interest rate (grants, subsidies, guarantees, subvention). Those can't be ranked as loans and only surface through `/api/schemes/match` + `BenefitCalculator` (section 4). Only `state-ka-badavara-bandhu-2018` (3-month tenure) is dropped for tenure shape; PM Vishwakarma (2.5y) is now included.
9. Simulated (Python mirror of the Java filters, 2026-09-22): baseline applicant, all 3 villages x 4 categories x margins 10k-500k -> 1-2 schemes, identical across states: Mudra Kishor (loan up to 5L) or Tarun (5-20L), plus PMEGP for every non-dairy category; Dairy with a Rs 45L loan (margin 5L) gets none, so the analysis throws. With `applicant` details: maratha_ebc in Maharashtra unlocks Annasaheb Patil (0%, 10-50L), SC + income <= 3L unlocks NSFDC term loan, artisan unlocks PM Vishwakarma. **Only central schemes are ever returned for the baseline applicant** — every state scheme in the dataset gates on something (state + caste, state + age band, state + occupation, ...) the baseline doesn't claim; central schemes have broader, mostly age/sector-only gating. State schemes only start appearing once the frontend actually sends `applicant` details (section 4).
10. **DONE 2026-09-22: ranking now checks affordability and subsidy, not just total repayment.** Total repayment alone favoured short, high-EMI loans a business can't actually service (see the NSFDC-vs-Kishor example in section 4, now resolved by this). `FinancialCalculatorService` computes `monthlyNetOperatingIncome = referenceMonthlyRevenue - referenceMonthlyOperatingCost` per category and ranks: affordable options (EMI <= that figure) before unaffordable ones, then lowest net cost (`totalRepayment - estimatedSubsidy`), then lowest EMI, then scheme_id. If nothing is affordable, the same order applies among unaffordable options (cheapest first) and DSCR will show Risky — the analysis never throws just because nothing is comfortably affordable. `estimateSubsidy` only nets `benefit.calculation_type == "pct_of_loan_capped"` (min(subsidy_pct% of loan, max_subsidy_amount), a max_subsidy_amount of 0 counts as no subsidy) — other calculation types reuse `subsidy_pct` for unrelated things (interest subvention %, share of project cost, guarantee cover %) so netting them would be wrong; that's `BenefitCalculator`'s job later (section 4b is now superseded by this — mark it DONE, not pending).
11. **DONE 2026-09-22: ~20 bank loans that had no `interest_rate` now get one.** They're real loans (Stand-Up India, AIF, AHIDF, MP Birsa Munda/Tantya Mama, Gujarat DTAISY, TN NEEDS/AABCS, etc.) where the government subsidises part of the interest but doesn't fix the bank's own rate, so the dataset left `interest_rate` null and they were invisible to the whole loan-ranking pipeline. New `src/main/resources/data/scheme_rate_overrides.json` records, per scheme, the subvention percentage and (where the note is explicit) how many years it lasts, a lending-rate cap where the scheme states one, and an overridden assumed bank rate where the note gives one (Stand-Up India: MCLR+3%). `SchemeDataService.estimateRate` = assumed bank rate (10.5%, `ASSUMED_BANK_RATE_PERCENT`, between Mudra's 9.5-10% and PMEGP's 11%) minus the subvention, prorated by `subventionYears / tenureYears` when the subvention doesn't cover the full tenure, floored at 0%, capped at the scheme's stated max lending rate. Result written to `interestRate` with `rateEstimated = true`; schemes that already carry a rate, or have no override entry, are untouched. Deliberately NOT netted: the capital/FCI/margin-money subsidies most of these schemes ALSO carry (e.g. TN AABCS's 35% capital subsidy on top of its 6% subvention) — those aren't interest, so `estimateSubsidy` (2.10) doesn't count them either; a scheme's true cost is therefore still understated where both apply. `state-gj-sky-2018` and a few other schemes have `interest_rate` already set from the dataset alongside a `loan_amount_range` of `{min:0,max:0}` — that's the "no stated limit" case fixed in finding 8, not a rate issue.

## 6. Full-Schemes-Browse feature — roadmap (added 2026-09-22)
### Read this before touching the schemes-match/browse work. Supersedes the "next chunk" note at the end of section 4a with locked-in decisions.

**The problem this solves**: right now the only schemes a user ever sees are the 1-2 (occasionally 3, with PMEGP) that `SchemeComparisonTable.jsx` renders from `/api/analyze`'s ranked top-5, because the analyze flow only ever sends a baseline applicant (no caste/gender/income/sector specifics), so all 150 state schemes fail their eligibility rules. This roadmap replaces that with: **all eligible schemes across every type** (loans, grants, subsidies, guarantees — not just the 47 loan-type ones), **filterable**, showing the **5-7 best matches + "see more"**, and a **click-through detail view** per scheme.

- Scope: ALL calculation_types, not loans-only. Plus filters (level central/state, sector, state, calculation_type/benefit-kind) so the user can narrow the set themselves.

- Placement: new dedicated page/route (not crammed into the existing analyze results page) — analyze results keeps its current quick loan-comparison table as-is; the new page is the full browse experience, linked from analyze results via a CTA.
